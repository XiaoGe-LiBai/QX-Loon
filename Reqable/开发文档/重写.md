重写是 Reqable 的核心调试功能之一，通过预设规则自动修改请求或者响应。Reqable 的重写支持 5 种模式，分别是[重定向](#redirect)、[替换请求](#replace-req)、[替换响应](#replace-res)、[修改请求](#modify-req)和[修改响应](#modify-res)。

重写功能可以通过四种方式启用或关闭：

*   直接点击重写图标
*   右键重写图标 -> 启用 / 禁用
*   托盘 -> 重写 -> 启用 / 禁用
*   快捷键 `Shift + Control + K`

![](https://reqable.com/zh-CN/assets/images/rewrite_01-83b4af43bd97ecfa683b7e58cb3ed80f.png)

>信息
>
>为防止功能滥用，Reqable 在移动端不提供此功能。

### 创建规则[​](#创建规则 "创建规则的直接链接")

创建一个重写规则有下面六种方式：

*   右键重写图标 -> 新建规则
*   托盘 -> 重写 -> 新建规则
*   重写列表 -> 点击右上角 `+` 号图标
*   重写列表 -> 右键菜单 -> 新建
*   调试列表 -> 选中一个列表项 -> 右键菜单 -> 重写
*   快捷键 `Shift + Alt + K`

![](https://reqable.com/zh-CN/assets/images/rewrite_02-3b3006f473cda23c4fcbe0bb214d8cfe.png)

输入规则名称和匹配的 URL，URL 支持简单的 Wildcard * 和 ? 匹配，最后设置一个重写行为，Reqable 支持以下五种重写行为。

*   [重定向](#redirect)
*   [替换请求](#replace-req)
*   [替换响应](#replace-res)
*   [修改请求](#modify-req)
*   [修改响应](#modify-res)

重写行为的优先级是 重定向 > 替换 > 修改，如果一个请求同时被以上三者匹配到，会按照这个优先级顺序进行执行。

*   一个请求最多只能触发一个重定向规则。
*   一个请求可以触发多个替换规则，按照规则列表中的前后顺序执行。
*   一个请求可以触发多个修改规则，按照规则列表中的前后顺序执行。
*   替换和修改规则会匹配重定向后的新 URL 而不是原始请求 URL。

### 重定向[​](#redirect "重定向的直接链接")

相比于[镜像](https://reqable.com/zh-CN/docs/capture/mirror)功能，重写重定向提供了更加细粒度的重定向操作，例如一个客户端请求 A：`https://hello.com/foo`，可以重定向为返回请求 B：`https://world.com/bar` 的结果。重写重定向属于请求转发，可以理解为`Map Remote`，和 HTTP 协议 3xx 状态码的重定向不同。

![](https://reqable.com/zh-CN/assets/images/rewrite_12-dad2573d88c853b2ad28dc0828a7084d.png)

上图是重定向编辑页面，有几点需要注意：

*   **保留头部 Host** 请求新 URL 地址时，请求头部的 Host 值是否为原地址的 Host。此选项一般不建议开启，不同服务端框架对 Host 的处理逻辑不同，可能导致请求失败。
*   **目录匹配** 如果新 URL 地址以 /* 结尾，表示匹配原地址的子目录。
*   **排除 URL** 这是可选项，当被重定向的 URL 需要排除时（即不重定向）可以配置此项。

下面是一个重定向的示例，假如我们需要将下面的 URL 设置一个重定向：

```
https://hello.com/foo/bar/ok?abc=123
```

重定向为
```
https://world.com/new/*
```

那么实际重定向的 URL 为

```
https://world.com/new/foo/bar/ok?abc=123
```

>警告
>
>1.  当前版本的实现下，如果原请求的服务器地址无法响应，会直接导致请求失败（即不会发起重定向请求）。
>2.  每个请求最多只能触发一个重定向规则，即列表中从上往下最先匹配到的规则。

### 替换请求[​](#replace-req "替换请求的直接链接")

此重写行为表示整体替换请求数据，支持替换的部分包括：请求方法、请求路径、请求头和请求体。

>小技巧
>
>从调试列表右键菜单创建一个替换请求规则时，请求的数据会自动填充进来，我们只需要稍作修改即可。

#### 替换请求方法和路径[​](#替换请求方法和路径 "替换请求方法和路径的直接链接")

无论原始请求方法和路径是什么，都会被替换成预设的请求方法和路径：

![](https://reqable.com/zh-CN/assets/images/rewrite_03-ef8ac98a231db8b40b088ae236b291a1.png)

无论原始请求头是什么，都会被替换成预设的请求头：

![](https://reqable.com/zh-CN/assets/images/rewrite_04-b31b53bd98455ac7c6999201c51fc445.png)

>关于 Content-Length
>
>无论是否有预设 Content-Length，最终 Content-Length 的值都会根据编码方式自动重新计算。所以替换头部的时候无需关心 Content-Length。

#### 替换请求体[​](#repleace-req-body "替换请求体的直接链接")

无论原始请求体是什么，都会被替换成预设的请求体：

![](https://reqable.com/zh-CN/assets/images/rewrite_05-e4eea91aea058852b38142817941ce4f.png)

Reqable 支持预设三种替换请求体类型：空、文本和本地文件。

### 修改请求[​](#modify-req "修改请求的直接链接")

相比于[替换请求](#replace-req)行为，修改请求提供了更加细致化的修改策略。例如删除查询参数，修改请求头中的某一项，正则替换请求体的内容。

举个例子。有下面这样的请求参数，我们希望修改 key 的值为 54321，但保留其他的参数不变。

```
https://reqable.com?key=12345&foo=bar&hello=world

```

现在只需要创建一个 key 的匹配替换规则即可：

![](https://reqable.com/zh-CN/assets/images/rewrite_07-000f88b77857adcdc53e7e948c63f6ee.png)

如果复杂一点，我们不知道 key 的具体值，但是仍然希望替换为 54321，可以使用正则表达式：

![](https://reqable.com/zh-CN/assets/images/rewrite_08-97746f005506d829ed6ff96d8da8f9aa.png)

再复杂一些，如果我们希望在原始 key 值的基础上加一个前缀 `api-` , 可以使用正则表达式和 `$` 分组替换：

![](https://reqable.com/zh-CN/assets/images/rewrite_09-191676f07dc0898c2ee29fecf91af734.png)

一个请求可以创建并应用多个修改规则，我们可以在列表中进行管理。

![](https://reqable.com/zh-CN/assets/images/rewrite_10-cd1f6b3744bc19098e9ea4cc22be3130.png)

>注意事项
>
>*   此模式不支持修改请求方法和请求路径。
>*   请勿修改请求头 Content-Length 的值，因为最终 Content-Length 的值都会根据编码方式自动重新计算。
